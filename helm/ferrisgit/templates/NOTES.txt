The database password, JWT_SECRET and SETTINGS_ENCRYPTION_KEY live in the {{ include "ferrisgit.secretName" . }} Secret,
which `helm uninstall` leaves in place{{ if .Values.persistence.keepOnUninstall }}, like the two volumes ({{ .Release.Name }}-storage and {{ .Release.Name }}-postgres-data; delete them by hand to wipe the data){{ else }}. persistence.keepOnUninstall is false, so `helm uninstall` deletes the volumes and everything on them{{ end }}.
Never delete the Secret while the database volume exists: SETTINGS_ENCRYPTION_KEY is what makes every stored CI
variable, webhook secret, SMTP password and TOTP secret readable, and it cannot be rotated. If you render this chart with
`helm template`, Argo CD or Flux instead of `helm upgrade`, `lookup` cannot see that Secret: pass secrets.postgresPassword,
secrets.jwtSecret, secrets.settingsEncryptionKey and secrets.bootstrapAdminPassword yourself, or every render invents new ones.

Rolling the release back (`helm rollback`, `--atomic` or an older image tag) does not undo database migrations. The server applies
the migrations it ships at every start and does not tolerate unknown ones: a release older than the newest migration recorded in
the database stops at startup with "failed to run migrations: VersionMissing(<n>)", and the pod restarts in a loop. That includes
the rollback that --atomic performs when a new release fails after its migrations ran. Only a restore of the database backup
taken before the upgrade, or deploying a release that contains that migration, brings it back. Back up the database and the
repositories volume before each upgrade.
